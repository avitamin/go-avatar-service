# Подтвержденные требования

Этот документ хранит подтвержденные требования, уточнения и договоренности по проекту "Аватарница".

## Назначение

- Фиксировать требования, которые были уточнены или подтверждены после исходного ТЗ.
- Отделять принятые договоренности от черновых идей и вариантов реализации.
- Использовать как источник актуальных ограничений для спеки разработки.

## Требования


* HTTP-сервер на Go с Chi.
* Хранилище метаданных — PostgreSQL.
* Хранилище файлов — MinIO.
* Асинхронная обработка — RabbitMQ + worker.
* Обязательные операции API: upload / get / delete / list / metadata / health.
* Soft delete обязателен.
* Валидация upload: размер файла, MIME, magic bytes.
* Поддерживаемые форматы upload: `jpeg`, `png`, `webp`.
* Максимальный размер файла: 10 MB.
* Миниатюры: `100x100` и `300x300`.
* Миниатюры всегда хранятся в `jpeg`.
* Оригинал хранится в исходном формате.
* `GET /api/v1/avatars/{id}` без `size` возвращает `original`.
* Поддерживается только параметр `size`: `original | 100x100 | 300x300`.
* Неподдерживаемый `size` → `400 Bad Request`.
* Параметр `format` в MVP не поддерживается.
* Read-endpoints публичные.
* `X-User-ID` обязателен только для изменяющих операций.
* Формат `X-User-ID`: строка `1..255`, allowlist-паттерн.
* `POST /api/v1/avatars`:

    * при обычном успешном сценарии → `201`
    * если publish в RabbitMQ не удался после сохранения ресурса → `201` и `status=failed`
* Внешний `status` в API только:

    * `processing`
    * `completed`
    * `failed`
* `failed`-записи не скрываются из list и metadata.
* Soft-deleted записи снаружи выглядят как `404` и отсутствуют в list.
* `DELETE /api/v1/avatars/{avatar_id}`:

    * `404`, если запись не найдена или уже удалена
    * `403`, если `X-User-ID` не совпадает с владельцем
    * `204`, если удаление успешно
* `DELETE /api/v1/users/{user_id}/avatar`:

    * разрешён только если `X-User-ID == user_id` из path
    * удаляет последнюю неудалённую запись с доступным original
* Текущая аватарка пользователя для user-based read:

    * выбирается как последняя неудалённая запись с доступным нужным variant
    * fallback на предыдущую доступную запись обязателен
* Для `GET /api/v1/users/{user_id}/avatar?size=...`:

    * fallback работает и для `original`, и для thumbnails
    * если после fallback подходящего variant нет → `404`
* Для `GET /api/v1/avatars/{avatar_id}?size=thumb`:

    * если конкретный variant доступен → `200`
    * если variant недоступен и статус `processing` → `409`
    * если variant недоступен и статус `failed` → `409`
* Если original отсутствует в MinIO:

    * file endpoint → `404`
    * metadata endpoint → `200`
    * наружный `status` нормализуется как `failed`
* Metadata:

    * возвращается для существующей неудалённой записи даже при проблемах storage
    * `dimensions` желательны, но не обязательны в контракте MVP
    * thumbnails включаются только если реально готовы
* Список аватарок пользователя:

    * только неудалённые записи
    * сортировка `created_at DESC`
    * без пагинации в MVP
    * минимальные поля: `id`, `user_id`, `url`, `status`, `created_at`
* URL в API — относительные пути.
* `url` в list и metadata — URL API сервиса, не прямой S3 URL.
* `/health`:

    * проверяет `postgres`, `minio`, `rabbitmq`
    * возвращает общий статус и статусы компонентов
    * при частичной деградации → HTTP `200`, `status=degraded`
* Единый JSON-формат ошибок:

    * обязательны `error.code`
    * обязательны `error.message`
    * `error.details` опционален
* Worker:

    * обязателен
    * должен быть базово идемпотентным
    * должен логировать дубликаты
    * retry обязателен в минимальном виде
* Физическое удаление файлов:

    * только worker после soft delete
* Миграции:

    * отдельный явный шаг
    * не автозапуск при старте server/worker
* Контейнеризация:

    * обязательны Dockerfile и Docker Compose
    * Kubernetes не входит в обязательный scope MVP
* Покрытие `>50%`:

    * считается по backend-пакетам с логикой сервиса и worker
* Access logs для HTTP обязательны.

Web для MVP:

* Обязателен `GET /web/upload`.
* Используется шаблонный фронт из репозитория.
* Отдельный `POST /web/upload` не нужен.
* Upload из web идёт напрямую в `POST /api/v1/avatars`.
* `user_id` во фронте вводится пользователем через поле формы.
* Обязателен `GET /web/gallery/{user_id}`.
* Галерея:

    * только список
    * без удаления
    * показывает только записи, у которых доступен `original`
    * если доступен только `original`, запись всё равно показывается
    * если у пользователя нет записей в БД → `404`
    * если записи есть, но ни одна не подходит под фильтр → пустой список/пустая страница
* Для `GET /web/gallery/{user_id}`:

    * `user_id` валидируется по тем же правилам
    * невалидный `user_id` → `400`
* В галерее по умолчанию используется `original`.
